## 1. MIDI 的时间不是直接用秒记录

### 1.1 问题：按键时长是不是以 tick 为单位记录？

**回答：** 更准确地说，MIDI 通常不直接保存一个名为 `duration` 的字段，而是保存
Note On 和随后与它配对的 Note Off。两者的时间位置之差才是按键时长。

例如 `beyer-059-broken.mid` 中的一个 C4：

```text
absolute tick 7680：Note On，按下 C4
absolute tick 8405：Note Off，松开 C4

按键时长 = 8405 - 7680 = 725 ticks
```

Standard MIDI File 轨道中，每条消息的 `time` 通常不是 absolute tick，而是距离上一条
消息的 delta tick。解析器需要按顺序累加：

```text
absolute_tick[n] = absolute_tick[n - 1] + delta_tick[n]
```

随后使用 `(channel, note)` 找到相同音高、相同通道的 Note On 和 Note Off：

```text
key_hold_ticks = note_off_absolute_tick - note_on_absolute_tick
```

这里得到的是琴键保持时间，不等于声学上的发声时间。手指已经松键，但如果 CC64
延音踏板仍然踩下，声音还会继续；音源自身的包络和自然衰减也会影响最终听到的时长。

### 1.2 问题：如果松手正好发生在两个 tick 中间怎么办？

**回答：** 真实动作发生在连续时间中，但 MIDI 文件的 PPQ 时间位置只能保存整数 tick。
记录器会把传感器检测到的时间映射到一个可表示的整数位置。

Yamaha 没有在 CLP-835 文档中公开它采用四舍五入、向下取整还是其他映射策略。因此，
不能声称具体使用了哪一种。不过只考虑整数 tick 表示时，误差小于一个 tick；如果采用
最近 tick，最大误差是半个 tick。

这和乐谱量化不是同一个概念。假设 PPQ 为 1920：

```text
一个四分音符 = 1920 ticks
一个八分音符 =  960 ticks
一个十六分音符 = 480 ticks
```

原始演奏可以落在 725、1265、1505 等任意整数位置，并不会自动吸附到 480 的倍数。
“吸附到最近的八分或十六分音符”属于另外执行的 quantization。原始文件保留细粒度的
演奏偏移，量化则尝试恢复或强制建立乐谱网格。

## 2. PPQ：整个文件的音乐时间分辨率

### 2.1 问题：一拍多少 tick 是固定的吗？

**原问题中的易混点：** `mido` 将属性命名为 `ticks_per_beat`，很容易把它理解为口语中
任意拍号下的“一拍”。Standard MIDI File 的 PPQ 模式实际上定义的是：

> 每个四分音符包含多少 tick，即 pulses per quarter note。

**回答：** MIDI 标准没有规定所有文件必须使用同一个 PPQ。不同文件可以选择 96、240、
480、960、1920 等值；但在一个采用 PPQ 的 MIDI 文件内部，它是文件头中的全局值：

- 整个文件只有一个 PPQ；
- 所有轨道共用；
- 不能通过轨道中的事件在演奏中途改变；
- tempo 可以中途改变，PPQ 不可以。

Standard MIDI File 还允许使用 SMPTE 帧率作为时间基准；`mido` 会把这类文件的
`ticks_per_beat` 解码成负数。当前练习只分析 PPQ 时间基准，并会明确拒绝 SMPTE 文件，
避免把负值误传给 PPQ 换算公式而产生错误的负时长。

当前五份 CLP-835 文件都是：

```text
ticks_per_quarter = 1920
```

所以它们的乐谱时间单位是：

```text
全音符       = 7680 ticks
二分音符     = 3840 ticks
四分音符     = 1920 ticks
八分音符     =  960 ticks
十六分音符   =  480 ticks
```

### 2.2 “一拍”不一定等于一个四分音符

拍号会影响演奏者如何感受拍点，但不会改变文件的 PPQ。例如 PPQ 仍为 1920 时，6/8 拍中：

```text
一个八分音符       =  960 ticks
一个四分音符       = 1920 ticks
一个附点四分音符   = 2880 ticks
```

6/8 常把附点四分音符感受为一大拍，因此口语中的“一拍”可能是 2880 ticks。为了避免
歧义，分析程序和文档应优先写 `ticks_per_quarter`，或者明确这里的 beat 指四分音符。

### 2.3 PPQ 可以修改吗？

可以重写文件，但不能只改文件头。必须按比例缩放所有事件的 delta tick。例如从 1920
改到 960 时：

```text
new_tick = old_tick × 960 / 1920
```

所有 Note On、Note Off、Control Change、tempo 事件位置和其他 tick 时间都要一起缩放。
tempo 本身仍然表示“每个四分音符多少微秒”，不需要因为 PPQ 改变而同比例缩放。

如果只把头部的 1920 改成 960，却保留原事件 tick，原来的 1920 ticks 会从一个四分
音符变成两个四分音符，乐谱位置和播放时间都会改变。

把低 PPQ 文件改成高 PPQ 也不会凭空恢复精度。它只是把已有坐标乘大，类似把低分辨率
图片放大；只有记录时原本捕获到的时间信息才是真实信息。

## 3. Tempo、BPM 与 tick 到秒的换算

### 3.1 MIDI 中的 tempo 到底保存什么？

`Set Tempo` meta event 保存的是：

```text
microseconds_per_quarter_note
```

即一个四分音符占多少微秒。四分音符 BPM 的换算为：

```text
quarter_BPM = 60,000,000 / microseconds_per_quarter_note
```

如果文件还没有出现 Set Tempo，常用默认值是：

```text
500,000 微秒/四分音符 = 120 BPM
```

### 3.2 问题：一个 tick 的时值是否同时与 PPQ 和 BPM 有关？

需要把“乐谱时值”和“现实时间”分开。

在乐谱坐标中，只取决于 PPQ：

```text
1 tick = 1 / PPQ 个四分音符
```

在现实秒数中，同时取决于 PPQ 和当前 tempo：

```text
seconds_per_tick
= microseconds_per_quarter_note / 1,000,000 / PPQ
```

如果 BPM 明确指四分音符 BPM，也可以写成：

```text
seconds_per_tick = 60 / (quarter_BPM × PPQ)
```

当前文件 PPQ 为 1920。在 67 BPM 时：

```text
60 / (67 × 1920)
≈ 0.000466 秒
≈ 0.466 毫秒/tick
```

在 120 BPM 时：

```text
60 / (120 × 1920)
≈ 0.000260 秒
≈ 0.260 毫秒/tick
```

因此：

- PPQ 越大，一个 tick 占据的四分音符比例越小；
- BPM 越快，一个四分音符越短；
- 同一文件中 tempo 改变后，同一个 tick 对应的秒数也会改变；
- 跨越多个 tempo 区间的音符必须分段换算，不能只乘一个固定比例。

### 3.3 BPM 必须带上拍子单位

音乐中的裸数字“67 BPM”并不完整，应说明哪个音符每分钟出现 67 次：

```text
四分音符 = 67：quarter BPM = 67
二分音符 = 67：quarter BPM = 134
附点四分音符 = 67：quarter BPM = 100.5
```

MIDI 的 Set Tempo 始终以四分音符为换算基准。`mido.tempo2bpm()` 默认给出的也是
四分音符 BPM。它不能直接代替谱面上可能以二分音符或附点四分音符为单位的速度标记。

## 4. 文件中的 67 BPM 是怎么来的？

### 4.1 问题：钢琴在录制前会估算演奏者的 BPM 吗？

**回答：** CLP-835 的普通 MIDI 录音不会先听演奏再估算 BPM。它使用当时的内部 tempo
设置建立时间坐标，即使节拍器没有发声，内部时钟和当前 tempo 仍然存在。

当前五份文件都有相同的 tempo 事件：

```text
tick 0：
    tempo = 500000 μs/四分音符
    quarter BPM = 120

tick 7680：
    tempo = 895545 μs/四分音符
    quarter BPM ≈ 66.998，也就是约 67
    第一批 Note On 同时开始
```

所以 0～7680 是使用 120 BPM 的无音符前导区间；从第一批演奏音符开始，生效的
MIDI tempo 是四分音符约 67 BPM。为什么钢琴当时的当前设置恰好是 67，仅靠文件不能
反推出具体操作，但它显然不是根据演奏内容自动估算的结果：五份不同内容的录音都写入
完全相同的值。

### 4.2 文件 tempo 可以和实际演奏速度不一致

tempo map 是时间坐标系，不是对演奏者是否跟拍的评价。假设文件使用 67 BPM：

```text
一个名义四分音符 = 1920 ticks = 0.895545 秒
```

如果演奏者现实中每隔 0.594 秒按一次琴键，记录器仍然可以把它写成：

```text
0.594 秒 / 0.000466 秒/tick ≈ 1273 ticks
```

按相同 tempo map 播放时：

```text
1273 ticks × 0.000466 秒/tick ≈ 0.594 秒
```

因此回放时间仍然正确，但音符没有落在名义上的 1920-tick 四分音符网格上。

### 4.3 用拜厄 61 验证 67 是否符合实际演奏

拜厄 61 左手是稳定的四分音符型，每相邻两个左手起音对应一个四分音符。对
`beyer-061.mid` 的实测结果是：

```text
左手 Note On：63 个
相邻间隔：62 个

平均间隔：0.594 秒
中位间隔：0.590 秒
大部分间隔：0.541～0.651 秒

平均 tick 间隔：1273.4 ticks
中位 tick 间隔：1265 ticks
```

若每个间隔是一个四分音符，则实际演奏速度约为：

```text
60 / 0.594 ≈ 101 BPM
60 / 0.590 ≈ 102 BPM
```

所以这次演奏的中心速度约为四分音符 101～102 BPM，并且存在自然波动；它与文件的
四分音符 67 BPM 不一致。文件中的 67 是录音时使用的 tempo 坐标，不是钢琴从演奏中
估计出的速度。

这个结论对后续节拍与乐谱分析很重要：

> 不能直接把 MIDI 中的 Set Tempo 当作演奏者的真实 beat；需要结合谱面时值、周期性、
> 拍点估计或参考乐谱对齐重新建立演奏 tempo map。

## 5. 一次下键记录了多少“力度”信息？

### 5.1 标准 Note On 本身只有一个 velocity 字段

传统 MIDI 1.0 Note On 主要包含：

```text
channel
note number
velocity（1～127；0 通常解释为 Note Off）
```

这里的 velocity 更接近琴键下落、触发琴槌时的速度，而不是以牛顿测量的手指压力。
一般而言，下键越快，琴槌撞弦越快，声音更响且起音更明亮。

### 5.2 CLP-835 的一次下键不只有普通 velocity

当前 CLP-835 文件在几乎每个 Note On 前都写入：

```text
CC19       Key Acceleration
CC88       High-Resolution Velocity Prefix
Note On    note number + velocity
```

例如拜厄 61 第一个右手音：

```text
tick 7680：CC19 value=32
tick 7680：CC88 value=119
tick 7680：Note On note=83 velocity=55
```

CC88 是高精度 velocity 的低 7 位，Note On velocity 是高 7 位：

```text
velocity_14bit = note_on_velocity × 128 + CC88
```

这个音得到：

```text
55 × 128 + 119 = 7159
```

因此 `55` 和 `119` 不是两种独立力度，而是同一个高精度下键速度的高位和低位。
普通接收器可以只读取 Note On 的 7-bit velocity；理解 CC88 的接收器可以得到更细的
14-bit 分辨率。

CC19 则是另一项独立特征。Yamaha 将它定义为 `Key Acceleration`，即映射到 0～127 的
下键加速度数据。这个值没有公开的物理单位，不能把 `CC19=32` 解释为 `32 m/s²`。

### 5.3 松键和按住期间记录了什么？

标准 Note Off 可以携带 release velocity，但当前五份文件的所有 Note Off 都是：

```text
velocity = 64
```

固定值不能用来比较哪次松键更快，因此当前数据没有通过 Note Off velocity 保存真实的
松键速度差异。

每个音在 Note Off 前还出现一次：

```text
Polyphonic Aftertouch value=18
```

它在五份文件中始终固定为 18，并且通常只出现一次，不是一条连续压力曲线。Yamaha
官方 Data List 只将其列为 Polyphonic After Touch，没有进一步公开这个固定值在内部
音源中的详细解释。从位置和形态看，它更像琴键回升期间的释放或制音转换标记；当前
分析不应将它解释为“按住琴键期间的手指压力”。

因此一次 CLP-835 触键可以概括为：

```text
下键
├── note number
├── Note On + CC88：高精度下键速度
└── CC19：下键加速度

保持
└── 没有完整、连续的键位或手指压力曲线

松键
├── 固定 Polyphonic Aftertouch 18
└── 固定 Note Off velocity 64
```

## 6. 下键加速度与机械钢琴音色

### 6.1 问题：机械钢琴中加速度真的会影响音色吗？

**回答：** 琴槌撞弦速度仍然是决定音量和主要音色的核心变量；下键加速度可能影响更
细微的起音质感，但不能理解为“按住以后继续用力就能改变已经发出的声音”。

机械过程可以简化为：

```text
手指运动
  ↓
琴键和联动机构运动
  ↓
琴槌在 escapement 附近脱离驱动
  ↓
琴槌自由撞击琴弦
  ↓
琴弦、音板和琴体振动
```

琴槌速度会影响输入琴弦的能量、琴槌毡的非线性压缩、接触时长和高频泛音比例。因此
速度变化往往同时带来响度和音色变化。

但真实机构不是完全刚性的。两个触键可能在某一测量位置具有相近速度，却具有不同的
速度轨迹和加速度：

```text
触键 A：较早加速，接近 escapement 时趋于平稳
触键 B：前段较慢，接近 escapement 时突然加速
```

可能受到影响的部分包括：

- 琴槌柄的细微弯曲和振动状态；
- 琴槌头与琴弦的接触位置和擦动方式；
- 手指撞击琴键与琴键触底的机械噪声；
- 多个音之间的微小时序和同步关系。

2014 年的感知实验表明，即使琴槌速度相同，听众仍可能区分按压式和敲击式触键；其中
很大一部分信息来自手指—琴键和琴键触底噪声，去除这些声音后区分效果会消失。

2025 年 PNAS 的研究进一步使用高精度、非接触键位传感器。在单音验证实验中，研究者
尝试让两个触键的 escapement 速度、时长和起止噪声等差异小于 4%，同时让 escapement
加速度相差超过 12%；专业钢琴家仍能系统地区分音色。研究提出琴槌柄柔性可能影响琴槌
触弦方式，但没有直接测量钢琴内部机构，因此具体机械路径仍是推断。

对当前学习最稳妥的结论是：

1. 先把 velocity 看作主要变量；
2. CC19 可能为数字钢琴建模提供额外触键信息；
3. 它不等于完整的手指动作，也不能单独解释全部音色；
4. 对真实演奏的音色分析仍需音频、连续键位传感器甚至视频。

## 7. CC19、CC64、CC88 为什么这样命名？

### 7.1 Control Change 消息结构

`CC` 是 `Control Change` 的缩写。一条 MIDI 1.0 Control Change 消息包含：

```text
channel：MIDI 通道
control：控制器编号，0～127
value：该控制器的新值，0～127
```

例如：

```python
control_change(channel=0, control=64, value=127)
```

表示在 Python 零基的 channel 0 上，把 64 号控制器设为 127。`CC64` 中的 64 只是
控制器编号，不是踏板深度、力度或者 bit 数；实际状态在 `value` 中。

控制器编号来自 MIDI 的注册表。部分编号有跨设备通用语义，部分是 general purpose、
undefined 或留给更具体的实现使用。

### 7.2 三个控制器的语义和可移植性

| 控制器 | MIDI 基础语义 | CLP-835 中的语义 | 可移植性 |
|---|---|---|---|
| CC19 | General Purpose Controller 4 | Key Acceleration | Yamaha 实现语义，其他音源可能忽略 |
| CC64 | Damper/Sustain Pedal | 连续延音踏板位置 | 通用，半踏板曲线仍可能因设备不同 |
| CC88 | High Resolution Velocity Prefix | 下一条 Note On/Off velocity 的低 7 位 | 标准扩展，但并非所有音源支持 |

CC19 在基础 MIDI 注册表中只是 General Purpose Controller 4。Yamaha 在自己的 MIDI
Implementation 中规定它表示 Key Acceleration。接收端如果不了解 Yamaha 约定，可能
把它当作普通通用控制器或直接忽略。

CC64 的传统开关解释是：

```text
0～63：off
64～127：on
```

但支持半踏板的钢琴可以保留整个连续范围。`note-pedal-test.mid` 实际记录的踩下过程为：

```text
0 → 7 → 25 → 57 → 71 → 77 → 88 → 96 → 113 → 127
```

松开时又逐步经过 111、93、78、63、52、32、19、6，最后回到 0。这说明 CLP-835
保存了连续踏板运动，而不是只在阈值两侧写两个状态。分析程序把 `>=64` 统计为 down
适合做粗略开关计数，但不能代替半踏板曲线分析。

CC88 是标准化的 High Resolution Velocity Prefix。它作用于紧随其后的 Note On 或
Note Off；旧音源可以忽略它，支持该扩展的音源则把它作为低 7 位与普通 velocity 合并。

## 8. MIDI 不只是钢琴格式

### 8.1 问题：MIDI 能表达其他乐器吗？

**回答：** MIDI 是通用的演奏与控制协议，不是钢琴专用格式。一条基础 Note On：

```text
channel=0, note=60, velocity=80
```

只表示在指定通道以给定速度启动某个音高，并没有直接声明“这是钢琴”。最终声音取决于：

- 接收音源或软件加载了什么音色；
- Bank Select 和 Program Change；
- MIDI channel 的路由；
- 设备自身的音色库和厂商扩展。

同一条 Note On 可以驱动钢琴、小提琴、吉他、长笛、合成器或其他音源。General MIDI
进一步约定通用的 program 编号和鼓组映射，以提高不同设备之间的回放一致性，但具体
音色质量仍由音源决定。

### 8.2 不同乐器常用的控制信息

| 乐器或音源 | 常见 MIDI 表达 |
|---|---|
| 钢琴 | Note On/Off、velocity、CC64 延音、CC66 保持音、CC67 柔音 |
| 吉他 | Note On/Off、Pitch Bend、滑音、弦级控制或 MPE |
| 小提琴 | 连续 Expression、Pitch Bend、颤音、弓压映射或 MPE |
| 管乐器 | CC2 Breath、CC11 Expression、吐音、Pitch Bend |
| 鼓 | note number 对应底鼓、军鼓、踩镲等，velocity 对应敲击强度 |
| 合成器 | 滤波器、共振、包络、调制轮、aftertouch 和大量自动化控制 |

常见 CC 例子包括：

```text
CC1   Modulation Wheel
CC2   Breath Controller
CC7   Channel Volume
CC10  Pan
CC11  Expression
CC64  Damper/Sustain
CC74  Brightness
```

### 8.3 MIDI 文件还可以保存哪些事件？

除 Note On/Off 和 Control Change 外，常见 MIDI 消息还包括：

- Program Change：切换音色；
- Pitch Bend：连续弯音；
- Polyphonic Key Pressure：单个音符的触后控制；
- Channel Pressure：整个通道的触后控制；
- System Exclusive：不属于 channel voice message，用于设备或厂商专用数据。

Standard MIDI File 还可以保存不直接发声的 meta event：

- Set Tempo；
- Time Signature；
- Key Signature；
- Track Name；
- Marker、Lyric；
- End of Track。

MIDI 保存的是演奏指令，不是音频波形：

```text
MIDI：何时演奏哪个音、速度多少、控制器怎样变化
音频：扬声器最终产生的连续采样波形
```

## 9. MIDI 不是完整乐谱

即使 MIDI 保存了丰富的演奏事件，它通常仍然不知道：

- 一个音属于左手、右手还是某个内声部；
- pitch 61 应写成 C# 还是 Db；
- 短音是谱面上的 staccato，还是演奏者提前松手；
- 一组时间不齐的音是否本来是同一个和弦；
- 节奏应写成普通音符、附点、连音还是三连音；
- 演奏中断是休止符、换气、失误还是重来；
- 乐句、指法、表情记号和谱面排版。

因此“演奏 MIDI 转规范乐谱”仍然需要：

```text
原始 MIDI 事件
  ↓
tempo / beat 估计
  ↓
节奏量化与和弦聚类
  ↓
声部和左右手分配
  ↓
调性、和声与拼写推断
  ↓
MusicXML / 乐谱排版
```

这里也解释了为什么文件中的 Set Tempo、channel 或 note duration 都不能直接当作最终
乐谱答案：它们是重要观测，但不是完整音乐语义。

## 10. 本周形成的关键结论

1. 音符时长来自 Note On 与 Note Off 的时间差，不是 MIDI 中独立保存的 duration。
2. PPQ 是整个文件共享的每四分音符 tick 数；拍号和 tempo 都不会在中途改变 PPQ。
3. tick 的乐谱比例只由 PPQ 决定，tick 的现实秒数由 PPQ 和当前 tempo 共同决定。
4. 文件 tempo 是时间坐标，不保证等于演奏者真实速度；拜厄 61 实测约为四分音符
   101～102 BPM，而文件写的是约 67 BPM。
5. CLP-835 不仅记录普通 velocity，还记录 CC88 高精度低位和 CC19 下键加速度。
6. 当前文件的 Note Off velocity 固定为 64，不能用于分析真实松键速度。
7. CLP-835 的 CC64 保存连续踏板曲线，不能只当作二值事件。
8. MIDI 是跨乐器的演奏控制协议；钢琴事件只是其中一种使用方式。
9. MIDI 不是完整乐谱，自动写谱仍需恢复节拍、量化、声部和记谱语义。
